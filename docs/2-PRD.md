## 1. 개요

- **제품명**: 응모해
- **목적**: B2B 식자재 구매 고객(거래처)이 진행 중인 프로모션을 조회하고 DIRECT(일반 응모) 또는 ROULETTE(룰렛) 방식으로 참여할 수 있는 웹 애플리케이션. 관리자는 프로모션을 등록·관리하고 참여 현황을 확인한다.
- **배경**: 거래처 대상 프로모션 운영을 위한 전용 채널이 없어, 참여 접수·결과 확인을 위한 최소 기능의 웹앱이 필요함.
- **엔티티/규칙 상세**: `docs/1-domain-definition.md` 참조. 본 문서는 이를 전제로 제품 범위·일정·우선순위를 정의한다.

## 2. 목표 및 성공 지표

| 목표 | 지표 | 목표치 |
|------|------|--------|
| 거래처 회원 확보 | 가입 완료(User) 수 | 1,000개 이상 |
| 프로모션 기능 이용 확산 | 프로모션 참여(Participation 생성) 거래처 수(누적, distinct User) | 3,000개 이상 |

> "3,000개 이상 거래처 이용"은 1,000개 목표보다 큰 수치이므로, 신규 유입 지속 + 거래처당 복수 프로모션 참여를 함께 가정한 목표로 해석한다(이번 릴리스에서 별도 유입 시책은 범위 밖, §4 참조).

## 3. 대상 사용자

| 액터 | 요약 |
|------|------|
| 거래처 담당자 (User) | 외식업체/급식업체 등 B2B 고객사 소속. 프로모션 조회·참여가 주 목적. 현장(모바일)에서 접속 |
| 관리자 (Admin) | 프로모션 등록·관리, 참여 현황 확인. 사무실(데스크탑)에서 접속 |

상세 페르소나/시나리오는 이번 범위에서 작성하지 않음.

## 4. 범위

### In scope (MVP)

- 회원가입/로그인(User, Admin)
- 프로모션 목록/상세 조회
- 프로모션 참여(DIRECT/ROULETTE), 참여신청 상태전환(신청/취소/재신청)
- 내 참여내역 조회
- 관리자: 프로모션 등록/수정/조기종료, 참여 현황 조회
- 마이페이지(정보 조회/수정, 비밀번호 변경)
- 반응형 UI(모바일/데스크탑)

### Out of scope

- 실제 주문/결제/정산 연동, 재고 실시간 연동
- 승인 워크플로우, 거래처 등급별 차등가, 포인트 적립
- 검색 기능, 경품 재고 관리, 쿠폰 발급, 개인화 추천
- 접근성(a11y) 대응, 별도 마케팅/유입 시책, 통계 대시보드·리포트 고도화

## 5. 기능 요구사항 (우선순위)

3일 일정 기준, Day 단위로 구현 순서를 잡는다. 상세 구현 계획은 §8 참조.

| 우선순위 | 기능 | 비고 |
|----------|------|------|
| Must (Day1) | 회원가입/로그인(User, Admin) | 인증 없이는 이후 기능 진행 불가 |
| Must (Day1) | 프로모션 목록/상세 조회 | 관리자 등록 데이터 노출 전제 |
| Must (Day1) | 관리자 프로모션 등록/수정 | User 참여 기능의 선행 데이터 소스 |
| Must (Day2) | 프로모션 참여 - DIRECT | 응모 1회, result=PENDING |
| Must (Day2) | 프로모션 참여 - ROULETTE | 시도별 WIN/LOSE 즉시 확정, maxParticipationCount 제한 |
| Must (Day2) | 참여신청 상태전환(취소/재신청) | 기존 레코드 status 전환 |
| Should (Day2~3) | 내 참여내역 조회 | User 마이페이지 하위 |
| Should (Day3) | 관리자 참여 현황 조회 | 참여자 수, 당첨 현황 |
| Should (Day3) | 마이페이지(정보 수정, 비밀번호 변경) | User/Admin 공통 |
| Should (Day3) | 관리자 프로모션 조기종료 | status→ENDED, 기존 참여 보존 |
| Could | UI 폴리싱, 로딩/에러 상태 다듬기 | 시간 남으면 |

## 6. 기술 스택 및 아키텍처 개요

| 영역 | 스택 | 선정 이유 |
|------|------|-----------|
| 프론트엔드 | React 19, Zustand(전역 상태), TanStack Query(서버 상태) | 인증 상태는 Zustand로, 서버 데이터(프로모션/참여내역)는 TanStack Query로 분리해 캐싱·재요청 로직을 직접 구현하지 않음 |
| 백엔드 | Node.js + Express, pg | 1인 개발 3일 일정에 맞는 최소 구성. ORM 없이 pg로 직접 쿼리해 러닝커브·설정 비용을 줄임 |
| DB | PostgreSQL 17 | 도메인 엔티티(User/Admin/Promotion/Participation/ParticipationAttempt)가 관계형 구조에 자연스럽게 대응 |

구성: SPA(React) ↔ REST API(Express) ↔ PostgreSQL. 별도 BFF, 마이크로서비스, 캐시 레이어는 두지 않는다(오버엔지니어링 금지).

## 7. 비기능 요구사항

- **반응형 UI**: 모바일(거래처 현장)·데스크탑(관리자 사무실) 모두 CSS 반응형으로 대응. 별도 모바일 앱/전용 레이아웃 없음.
- **접근성**: 이번 프로젝트에서 고려하지 않음.
- **성능**: 별도 부하 테스트·캐싱 설계 없이 기본 쿼리 인덱스(PK/FK) 수준만 적용.
- **보안**: 비밀번호 해시 저장. 인증은 JWT 기반 access token(짧은 만료, API 인가에 사용) + refresh token(긴 만료, access token 재발급 전용) 조합으로 구현. 참여 API는 로그인(유효 access token) 필수(규칙1). 그 외 고급 보안(레이트리밋, WAF 등)은 범위 밖.
- **데이터 정합성**: (Promotion, User) 유일 Participation, ParticipationAttempt 불변(재추첨 불가) 등 도메인 규칙은 DB 제약(UNIQUE 등) + API 검증으로 보장.

## 8. 일정 (3일)

| 일차 | 내용 |
|------|------|
| Day 1 | DB 스키마 설계·생성, 회원가입/로그인(User/Admin) API+화면, 프로모션 등록(Admin)/목록·상세 조회(User) API+화면 |
| Day 2 | 프로모션 참여 API(DIRECT/ROULETTE)+화면, 참여신청 상태전환(취소/재신청), 내 참여내역 조회 |
| Day 3 | 관리자 참여 현황 조회, 마이페이지(정보수정/비밀번호변경), 프로모션 수정/조기종료, 반응형 스타일 점검 및 버그 픽스 |

## 9. 리스크 및 가정

- **1인 개발·3일 일정**: 테스트 자동화, 코드 리뷰, 상세 QA를 별도로 확보하기 어려움. 수동 스모크 테스트로 대체.
- **범위 고정 필요**: 일정 내 Must 항목 우선 완료, Should/Could는 시간 소진 시 다음 이터레이션으로 이월.
- **3,000개 거래처 이용 목표**: 이번 릴리스는 기능 제공까지가 범위이며, 실제 유입·이용 확산은 운영(공지, 영업 채널 등) 영역으로 이번 문서 범위 밖이라고 가정한다.
- **동시성**: ROULETTE 참여 횟수 제한(maxParticipationCount) 등 동시 요청 시 경쟁조건은 DB 제약(예: 트랜잭션 내 카운트 체크)으로 최소 방어하되, 고부하 상황의 정교한 락 설계는 이번 범위에서 제외.
